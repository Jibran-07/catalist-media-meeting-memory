# Technical Write-up: Meeting Memory

**Problem and architecture.** The test asks for a searchable memory of 138 messy AMI design meetings, 25 cross-meeting answers, and a briefing prepared before Team TS3012's final meeting. I separated a Next.js interface from a FastAPI service and PostgreSQL on Neon. The importer reads transcript files, preserves each original speaker turn and timestamp, and creates overlapping passages for retrieval. A generated `tsvector` column and GIN index make PostgreSQL full-text search practical without another database. The code is arranged as one Git repository with explicit setup commands. The intended hosting setup is Vercel for the interface and Render for the API.

**Model versus code.** Parsing, hashes, speaker boundaries, SQL filters, chronological ordering and exact-quote validation are deterministic Python or SQL operations. A model is warranted for interpreting unfinished speech, resolving pronouns, comparing proposals with later approved choices, and expressing conclusions briefly. The question-answering path searches indexed passages, expands original turns, asks the model to assess the evidence, and repeats the search if the model identifies a gap or only one meeting is represented. All model citations are checked against single original turns with at least six consecutive words before they can be shown. No answer is accepted just because the newest mention sounds decisive. The TS3012 brief is constrained to meetings a, b and c to prevent information from its final meeting entering the preparation.

**Actual work and limitations.** All 138 meeting files were parsed locally. I manually checked and assembled 25 official answers from original transcripts, using evidence from at least two meetings per question, and wrote a TS3012 brief with inline source quotations. The checked submission passes the citation validator. This file was **not generated by a running model**, because Neon credentials and a model API key were unavailable. The separate model-generation pipeline is implemented but its real connectivity and answer quality remain unverified. The backend unit and API tests passed locally, including a simulated duplicate-safe incremental import. A Next.js production build was unavailable because the required npm packages were absent from the environment.

**Independent evaluation.** I wrote 15 new, narrower questions with expected answers and original source-turn evidence. A basic offline lexical retrieval proxy found the right source turn in its top five passages for **8 of 15 questions (53.3%)**. Seven misses were real. For example, E01 and E02 concern TS3012's battery and rubber choices but do not retrieve the correct densely mixed speaker turn. E05 asks about the unpriced IS1009 voice recogniser but retrieves other cost-related passages. E06 misses the short IS1003 proposal to change wood to plastic. These are observed retrieval failures, not fabricated model answers. Without a live DB and model, I cannot claim end-to-end answer accuracy or three wrong model responses. These misses suggest better passage ranking, an additional targeted search and, only if measured improvements justify it, semantic retrieval.

**Measured ingestion and cost.** Five local full-corpus reading, parsing and passage-construction passes yielded a median of **0.083 seconds for 138 meetings** and **48,148 turns**, giving about **0.60 seconds for 1,000 similarly sized meetings** by linear extrapolation. This explicitly excludes database insertion, network latency, GIN index upkeep and any hosted inference. The sample has **4.47 MB** of source text and **7.91 MB** of overlapping passage text; extrapolating yields roughly **32.4 MB source plus 57.3 MB passages** for 1,000 meetings before relational rows and indexes. Ingestion itself requires **$0 in model API calls**. A complete cloud cost and latency figure cannot be honestly measured without Neon; the free tier might be sufficient if database storage and compute fit its current quotas. Answer generation is metered separately by the selected model provider.

**At 10,000 meetings.** Maintain incremental imports rather than reindexing everything, constrain retrieval by team and chronology, cap evidence given to the model, monitor index size and latency, and use production connection management. Add regression questions that test decisions reversing over time, verify citations mechanically, and distinguish uncertainty from confident answers. The measured source corpus is just a slice of that workload; live database benchmarking and continuous quality checks are required before claiming that scale.
